## Issue 草稿

**标题**：[Android] 全局搜索「全部」页收敛为分段预览 + 补文件段

**描述**

**复现步骤**

1. 打开会话列表页，点击顶部搜索框进入全局搜索页（此时已有「全部/聊天记录/联系人/群组/文件」
   五个分类 Tab）
2. 输入一个联系人、群组、聊天记录、文件均能命中 >3 条的关键词
3. 切到「全部」Tab 观察

**预期**

- 联系人、群组、聊天记录、文件四段各只显示前 3 条，超过 3 条时段末出现「更多」，点击切到
  对应分类 Tab 并带着当前关键词
- 段序固定：联系人 → 群组 → 聊天 → 文件（本端无云文档/网盘，这两类不实现）
- 快捷入口（"搜索更多联系人"）保持现位置不动，它是动作入口不是结果类别，不参与段序截断、
  不设分类 Tab、不出「更多」
- 聊天段按会话桶计数（一行一会话），不是按消息条数
- 「更多」统一不带总数（各段总数口径不一致：文件段没有总命中数，聊天段总数是可见性过滤前的
  近似值）
- 文件段要能搜到结果；单条点击行为与文件 Tab 一致，跳转到对应会话定位到该消息

**实际**

四个分类 Tab 本身已经建好、各自可用，但「全部」Tab 仍是把联系人、群组、聊天记录三段
全量铺开，没有任何截断，没有「更多」入口；且完全没有文件段——文件只能在文件 Tab 里单独
搜到，「全部」页看不到任何文件命中。

**缺口分析**

分类 Tab、筛选器、文件搜索能力本身在之前的改动里均已交付，本次缺口限定在「全部」Tab 的
聚合展示规则：

1. **分段截断缺失**：纯客户端 UI 缺口，`rebuildList()` 从未做任何数量限制。
2. **文件段缺失**：数据层已具备（`FilesSearchViewModel` 已在键入时跟其它 Tab 同步发
   请求），只是没有接入「全部」页的渲染，纯客户端缺口，不需要新的网络能力。

**本次不做**：云文档、网盘两类（明确不做，分类限定为联系人/群组/聊天/文件四类）；
联系人/群组/聊天各分类
Tab 自身的命中规则与排序（「全部」页的每段就是对应分类 Tab 当前结果的前 3 条，各分类 Tab
的逻辑将来如何演进，「全部」页自动跟随，本 Issue 不新增或修改任何命中/排序规则）。

## PR 正文草稿

**标题**：`feat(search): 「全部」页收敛为分段预览 + 补文件段`

**正文**：

```
Close #<创建后回填>

### 背景

此前已交付的改动把「联系人 / 群组 / 聊天记录 / 文件」四个分类 Tab 端到端建好（各自独立
RecyclerView + ViewModel + 筛选器），但「全部」Tab 本身仍停留在"一屏全量铺开"：联系人、
群组、聊天记录三段无限铺开，没有截断、没有「更多」，且完全没有文件段。本次把「全部」Tab
收敛成统一的聚合展示规则，并补上文件段。

### 改动

#### 1. 新增 `AllTabSectionBuilder`：分段截断 + 「更多」判定抽成纯函数

把 `GlobalActivity.rebuildList()` 里内联的分段拼接逻辑抽成独立对象，便于脱离 Activity
单测。四段统一规则：

- 截前 3 条（`SECTION_PREVIEW_LIMIT`，写死常量，不做远程配置）
- 原始数据量 > 3 时在该段末尾追加一个「更多」行，点击后切到对应分类 Tab（`setCurrentItem`），
  不带总数——文件段拿不到总命中数，聊天段总数是可见性过滤前的近似值，四类口径互不一致，
  统一不展示
- 段序固定为 联系人 → 群组 → 快捷入口（原位不动）→ 聊天记录 → 文件，不按命中数/相关度
  重排
- 快捷入口（"搜索更多联系人"）不参与截断、不设「更多」——它是动作入口，不是搜索结果类别
- 聊天记录段的「3 条」指 3 个会话桶，不是 3 条消息——`chatRecords` 本身就是桶粒度的
  `DataVO.LOCAL_MSG` 列表，截断判断用桶数量而非展开后的消息数

#### 2. 新增文件段

数据直接复用 `filesTabViewModel` 的既有结果——它已经在关键词输入时跟其它 Tab 同步发
请求，不新开一次网络调用，只是此前没人把这份结果接进「全部」页。

- `DataVO` 新增 `FILE`（携带 `FileHit`）和 `MORE`（携带跳转目标 Tab）两个 item type
- `GlobalAdapter` 新增对应渲染分支：文件行复用 `FilesTabAdapter.convert()` 的渲染逻辑
  （图标/高亮文件名/大小/发送人/时间），避免 `GlobalAdapter` 反向依赖 `FilesTabAdapter`
- 点击跳转会话的逻辑同样复制自文件 Tab 的点击监听器（解析 `message_seq` → `orderSeq` →
  跳转），保证单条点击行为与文件 Tab 完全一致
- 新增布局 `item_global_more_layout.xml`（"更多"行）与字符串资源 `search_more`（中英)

#### 3. 空态判定扩展

`updateAllEmptyView` 从"联系人/群段 + 聊天记录段两路都完成"扩展为三路（新增文件段
`filesLoaded`）：任一路完成即可退出 loading，但判定"真的无结果"要三路都完成且都为空。

### 影响范围排查

- `DataVO` 构造函数新增的 `fileHit` / `jumpTab` 两个字段均为带默认值的可选参数，追加在
  现有参数列表末尾，不影响任何既有构造调用点
- `rebuildList()` 内部实现改为调用 `AllTabSectionBuilder.build()`，数据量 ≤3 条时对外
  行为与改动前完全一致（无截断、无「更多」），仅在 >3 条时才产生新的截断/更多行为
- 文件 Tab 自身的分页/筛选/错误处理逻辑未改动，「全部」页文件段只读取
  `filesTabViewModel.state` 做展示，不影响文件 Tab 的既有行为

### 验证

- `:wkbase:testDebugUnitTest` / `:wkuikit:testDebugUnitTest` 全部通过，共 873 例
- 新增 `AllTabSectionBuilderTest`（10 例）：单段 ≤3 条不出「更多」、单段 >3 条截断且
  「更多」携带正确的跳转 Tab（联系人/群组/聊天/文件分别验证）、聊天段按桶数量而非消息数
  判断、空段整体不渲染、快捷入口原位插入且不截断/不出「更多」、段序固定为
  联系人→群组→快捷入口→聊天记录→文件、全部为空时返回空列表
- `:wkuikit:processDebugManifest` / `:wkuikit:mergeDebugResources` 通过
- 真机覆盖：搜索一个联系人/群组/聊天/文件均命中 >3 条的关键词，确认四段各显示 3 条 +
  「更多」；点击任一「更多」正确切到对应分类 Tab 且已有数据（不空转 loading）；点击文件行
  正确跳转到对应会话并定位到该消息；清空关键词后文件段跟其它段一样清空
```

## 不在本次范围内

- 联系人段、群组段的截取顺序依赖的相关度排序规则——该规则未上线前不保证最相关，本次按
  现有服务端返回顺序直接截前 3 条，相关度排序是独立的后续工作
- 云文档、网盘两类——明确不做，分类限定为联系人/群组/聊天/文件四类
- 「全部」页本身的命中规则与排序——本次只做聚合视图，各分类 Tab 的搜索/排序逻辑未来如何
  变化，「全部」页自动跟随，本次未新增或修改任何 Tab 自身的命中规则
